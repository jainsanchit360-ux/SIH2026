1. ALERT ARCHITECTURE
   - Persistent, lightweight operational warning system built on top of scientifically
     validated Phase 7 risk engine and Phase 8 FastAPI service.
   - Dual-mode architecture:
     a) Historical Prototype Alerts derived from actual processed Parquet datasets (2025-09-23).
     b) Simulated Demo Alerts generated from operator-triggered What-If scenarios.
   - Zero modification or mutation to scientifically validated Parquet files or trained ML models.

2. STORAGE METHOD
   - Local SQLite database: `data/alerts.db`
   - Native Python `sqlite3` module with transaction locking and parameterized queries.
   - Persistent across backend restarts without introducing external cloud/database dependencies.

3. ALERT SCHEMA
   - alert_id (TEXT PRIMARY KEY) e.g. ALT-HIST-GSI_SITE_01-20250923, ALT-SIM-GSI_SITE_01-1725642000
   - site_id (TEXT), site_name (TEXT), state (TEXT), district (TEXT)
   - created_at (TEXT ISO 8601), observation_date (TEXT YYYY-MM-DD)
   - risk_score (REAL 0-100), risk_level (TEXT HIGH/MODERATE/LOW/INSUFFICIENT_DATA)
   - severity (TEXT HIGH/MODERATE/LOW/INFO)
   - static_susceptibility_score (REAL), dynamic_trigger_score (REAL)
   - reason (TEXT), major_risk_factors (TEXT JSON array)
   - data_source (TEXT OFFLINE_HISTORICAL_CACHE | SIMULATED_DEMO)
   - simulation_mode (INTEGER 0 | 1)
   - status (TEXT NEW | ACKNOWLEDGED | MONITORING | RESPONSE_DISPATCHED | RESOLVED)
   - acknowledged_at (TEXT ISO 8601), acknowledged_by (TEXT)
   - response_notes (TEXT JSON array)
   - status_history (TEXT JSON array)
   - updated_at (TEXT ISO 8601)

4. ALERT GENERATION & DEDUPLICATION RULES
   - Generation Rule: Alerts are created when fused current risk score is >= 40.0 (MODERATE) or >= 70.0 (HIGH).
   - Historical Deduplication Rule: Unique composite key (`site_id` + `observation_date`). Synced deterministically on startup.
   - Simulation Rule: Generated instantly on demand during What-If demo scenario execution.

5. ALERT SEVERITY LOGIC
   - HIGH (Risk Score >= 70.0): Urgent operational warning requiring authority intervention.
   - MODERATE (Risk Score 40.0–69.9): Operational advisory / monitoring condition.
   - LOW (Risk Score < 40.0): Baseline normal condition (no active warning).
   - INSUFFICIENT_DATA: Data availability state (not a landslide warning).
   - Mandatory Wording: "PROTOTYPE OPERATIONAL WARNING — REQUIRES REGIONAL CALIBRATION"

6. WORKFLOW STATES & TRANSITION RULES
   - NEW -> ACKNOWLEDGED
   - ACKNOWLEDGED -> MONITORING or RESPONSE_DISPATCHED
   - MONITORING -> RESPONSE_DISPATCHED or RESOLVED
   - RESPONSE_DISPATCHED -> RESOLVED
   - Invalid state transitions (e.g. RESOLVED -> ACKNOWLEDGED or NEW -> RESOLVED) are strictly rejected with HTTP 422 Unprocessable Entity.

7. BACKEND ALERT APIs (FastAPI)
   - GET /api/v1/alerts : Filterable list of alerts (status, severity, site_id, simulation_mode)
   - GET /api/v1/alerts/summary : Operational summary statistics
   - GET /api/v1/alerts/active : Un-resolved active warnings (NEW, ACKNOWLEDGED, MONITORING, RESPONSE_DISPATCHED)
   - GET /api/v1/alerts/history : Complete chronological warning history
   - GET /api/v1/alerts/{alert_id} : Detailed alert payload with status history
   - POST /api/v1/alerts/{alert_id}/acknowledge : Operational acknowledgment endpoint
   - PATCH /api/v1/alerts/{alert_id}/status : Controlled state transition endpoint
   - POST /api/v1/alerts/{alert_id}/notes : Operational notes appending endpoint
   - POST /api/v1/demo/simulate-and-alert : Demo What-If simulation + instant alert generation
   - POST /api/v1/demo/reset : Safe purge of simulated demo alerts (preserves historical cache and Parquet data)
